# hook と保守の起動・期限切れ

- 登録するのは PostToolUse（git push 直後。push のあとに後段が失敗したコマンドは PostToolUseFailure）と SessionStart（`startup|resume`。取りこぼしの回収）。PostToolUse・PostToolUseFailure は Bash・PowerShell ごとの項目に、`if` を 1 つ持つ hook（`Bash(* push*)`・`PowerShell(* push*)`）として置く。正本は `connect::PUSH_RULES`、`hooks.json` との一致は `tests/plugin_layout.rs` が検査する。
- `handle_hook` は PostToolUse・PostToolUseFailure（同じ扱い）と SessionStart を処理する。旧登録の互換で Stop と UserPromptSubmit も受け付け、知らないイベント名は何もしない。Stop は新規登録せず、旧登録の検出・移行・解除のためだけに読む。
- PostToolUse は `payload_may_push` で、`push` の語を含まないコマンドを状態 DB・ロックに触れず終える。判定できない形は処理側に倒す（誤発火は無害）。
- 非同期の PostToolUse・SessionStart は poll ロックを `HOOK_LOCK_WAIT`（25 分）まで待つ。UserPromptSubmit と旧 Stop は待たずに見送る。
- **タイミング**: 種類ごとに `when`（`push` / `release` / `manual`）・`paths`・`min_interval_hours`（AND）。期限が来た種類だけを 1 回の worker で処理し、どれも期限前なら worker を起動せず処理済み位置だけを進める。絞った種類は publication 状態の `kinds` に記録し、再開はその集合で行う。種類ごとの状態は最終完了時刻（`kind_runs`）だけで、成功時（棄却は数えない）にだけ更新する。処理済み位置はリポジトリに 1 つで、最小間隔は「間隔が過ぎたあとの次の push」で評価する。`run-now` はタイミングを無視し、`--documents` で絞っても位置は進む。
- **worker の期限切れ**: `process::capture` が `ErrorKind::TimedOut` を返すのは終了・回収・pipe の読み切り・job の空きがすべて確認できたときだけで、これを「終了を確認できたタイムアウト」（`WorkerFailure.confirmed`）とする。非 Windows の managed 実行は子孫を止めないので確認できたと扱わず、確認できない場合は従来どおり何も戻さず `maint.timeout_stopped` で止める。確認できたタイムアウトは、(1) 追い修正中: 直前の起動の終了時点（起動前に生バイト列で持つチェックポイント。`state["after"]` のハッシュと一致したものだけ）へ、終了確認直後のハッシュと一致する許可パスだけを戻し（新規ファイルは削除）、追い修正を打ち切って保守後検査へ進む（ソフト違反は警告つき commit・push。警告は `timeout_note` を notes と履歴の理由に出す。範囲外変更があれば従来どおり違反で止まる。戻せないパスがあれば commit せず `maint.timeout_not_restored` で止める）、(2) 最初の起動: 範囲外検査と `after` の記録のあと、起動前に持った変更前（`before`）の生バイト列を `restore_checkpoint` で戻す（gitignore 済みの共有文書は git で戻せないため。持てなかったときだけ `discard_outputs` へ退避）。戻せたパスだけ `after` を `before` に揃え（同じ HEAD の run-now が食い違いで失敗しない）、戻せなかったパスは worker 終了時の記録のまま残して `maint.timeout_restored_kept` に挙げる（次の push では利用者の変更として扱い保守しない。run-now はそれらが変わっていない間だけ再試行でき、利用者が編集していれば `changed_after_record` で止まる）。`worker_failed`（`worker_timed_out`）にする。ready からの再開（`resume_fix`）は追い修正と同じ扱いで直前の `after` の内容へ戻して保守後検査へ進み、チェックポイントを持てなければ `maint.timeout_not_restored` で停止する。同じ対象コミット（HEAD が同じ）では hook は worker を再起動せず、新しい push（HEAD が進むと古い記録の解消で新しい保守になり、処理済み位置が進んでいないので全範囲を処理する）か run-now（force）で再試行する。
- **中断復旧の書きかけの扱い**: hook 本体がセッション終了などで kill されると publication が `worker_running` で残る。次の SessionStart・push で、`worker_quiescence_error`（Windows。コマンドラインが `--no-session-persistence` と `--dangerously-skip-permissions|--safe-mode` の両方を持つ claude/node/cmd だけを数える。条件式は `worker_command_filter()` で、順序・引用符・間の別引数に依存しない（`.cmd` シム経由でも一致する）。stop-review フックの `claude -p`（権限フラグが無い）は数えない。判定できなければ従来どおり見送る）を通り、`interrupted_ignored_error` の後、`interrupted_recovered` を保存する前に `discard_interrupted_outputs(root, state, head)` で、追い修正が書き始める前に中断した場合に直前の起動の出力を変更前へ戻す（追い修正が書き始めていれば触らない。最初の起動中の中断も触らない）。次の条件をすべて満たすときだけ `discard_outputs` を呼び、1 つでも欠ければ何も触らない（部分的に戻すと、移した先の新規文書だけ削除されて本文が失われるため）: (a) 記録の `head` が現在の HEAD と同じ、(b) `before` の全キー（変わっていないパスも含む）で現在のハッシュが `after` と一致（読めなければ不一致）、(c) `ignored_before` が配列で、変わったパス（`before`≠`after`）がその中に無い（旧形式で欠ける記録は触らない）、(d) 変わったパスに staged が無い。戻せたパスだけ `after` を `before` に揃え、通知はしない。`after` の測定値が保存されるのは worker の終了後なので、最初の起動中の書きかけ（`after`＝`before`）や、追い修正が書き始めた後の出力は残り、利用者の変更として扱う。
- **HEAD 変更を先に見る**: 保守後検査でハード違反があっても、worker の実行中に HEAD かブランチが動いていたら（変更なし完了の経路を除く）、出力を破棄せず `maint.head_changed_uncommitted` で止める（phase は ready・履歴は held・処理済み位置は進めない）。書きかけは利用者の作業と区別できないため。続く push で HEAD が進むと、古い記録の解消（現在も記録どおりの出力だけを戻す）を経て新しい保守が全範囲を処理する。
