# hook・Claude Code 設定・管理画面・プラグイン
- **プラグインのスキルは CLI を呼ぶ薄い層**。判断・検証・書き込みは `scriptura <cmd> --json` 側にあり。CLI の引数・出力を変えたら `plugins/scriptura/skills/*/SKILL.md` と README を合わせて直す。
- **hook の登録は PostToolUse・PostToolUseFailure（git push 直後。push のあとに後段が失敗したコマンドは後者）と SessionStart（`startup|resume`。取りこぼしの回収）**。PostToolUse・PostToolUseFailure は Bash・PowerShell ごとの項目に、`if` を 1 つ持つ hook（`Bash(* push*)`・`PowerShell(* push*)`。正本は `connect::PUSH_RULES`、`hooks.json` との一致を `tests/plugin_layout.rs` が検査する）。Stop は新規登録せず、旧登録の検出・移行・解除のためだけに読む（`connect --apply` と Setup 版の登録が外し、`--remove` は新旧どちらも外す）。`handle_hook` は PostToolUse（PostToolUseFailure は同じ扱い）・SessionStart と、旧登録の互換で Stop・UserPromptSubmit を受け付け（知らないイベント名は何もしない）、PostToolUse は `payload_may_push` で `push` の語を含まないコマンドを状態 DB・ロックに触れず終える。判定できない形は処理側に倒す（誤発火は無害）。非同期の PostToolUse・SessionStart は poll ロックを `HOOK_LOCK_WAIT`（25 分）まで待ち、UserPromptSubmit と旧 Stop は待たずに見送る。`~/.codex` は書かない。
- CLI の出力（JSON・人が読む形式・doctor）に秘密値を入れない。パス・設定の要約・件数・定型の語だけにする（例外: `docs show` は利用者が設定した `guidance` / `instructions` の本文を返す）。`claude auth status` は `maintenance::scrub_host_env` をかけ、終了コードと `authMethod` だけを見る。
- Claude Code の `settings.json` を書き換えるのは `connect claude-code --apply`（登録）、`connect claude-code --remove --apply`（解除）、旧 Stop 登録の自動移行、Setup 版の自動登録・解除（`connect::register_for_setup` / `refresh_for_setup` / `unregister_for_setup`。下の Setup の節）だけ。旧 Stop の移行は `hook` が Stop で呼ばれたとき `maintenance::run` が `connect::migrate_old_stop_registration` を呼ぶ形で、ユーザー単位の settings.json に自身の Stop hook があるときだけ（Setup 版は対象外。プラグイン有効時は外すだけで新登録しない）。実行中の本体を完全パス一致で指す Stop hook があるときだけ移行する（登録は実行中のパス）。移行直前の内容は `settings.json.scriptura-migration-backup[-N]` へ必ず残す。rename の直前に再読込みして、変わっていたら次の Stop に任せる。移行できたときだけ 1 回通知し、状態フォルダー・DB には触れない。別設定を壊さず、壊れた JSON は書き換えず、最初の変更前に退避する。`--remove` は Scriptura の項目だけを消し、`agents-maintenance` には触れない。
- プラグインのスキルの `allowed-tools` は、そのスキルが使うサブコマンドだけを `Bash(scriptura <sub> *)` の形で事前承認する（`tests/plugin_layout.rs` が検証）。ランチャー `plugins/scriptura/bin/scriptura` は Git Bash では `scriptura.exe` へ渡す。
- **管理画面（`src/ui/`）**: hook から独立させ、tokio は `ui::run` の中だけで初期化する。`127.0.0.1` だけに bind し、保護（Host → Origin / `Sec-Fetch-Site` → セッション Cookie → CSRF）は `guard` の 1 か所に集める。使い捨て鍵は一度だけ有効。設定を変える POST は `handlers::apply_change` を通し、版の照合と `confirm::dangers(before, after)` による二段階確認（1 回目は書き込まず、nonce は 10 分で失効）を強制する。設定の書き込みと `run-now` は `ops` の関数だけを呼ぶ。GET は状態フォルダー・DB・ロックを作らない。秘密値・環境変数を表示しない（エンジン由来の自由文は `views::redact` を通す）。ヘッダーは概要・リポジトリ・履歴（`/history`、保守履歴）・設定の 4 項目で、設定の下に共通のサブナビ（全般・文書 `/settings/documents`・worker・変更履歴 `/settings/history`・診断）。旧 `/kinds` `/proposals` `/consent` は 404。`ui::models` は「モデル一覧を更新」の POST のときだけ一覧を取る（詳細は DESIGN.md）。概要の「アプリの更新」パネル（`#updates`）は `POST /updates/*`（`guard` を通る）。60 分無操作・Ctrl+C・画面の「終了」で終わる。`ui --tray`（Windows・macOS だけ）は常駐で、終了もセッションの失効もせず、アイコンの「開く」のたびに使い捨て鍵を発行し直す。セッション Cookie 名はポートを含める（`session_cookie_name`）。トレイは `tray::Control` 越しにだけサーバーへ触れ、サーバーはワーカー側、OS のメッセージループはメインスレッドで動かす。feature `ui` なしのビルドが通ること。画面を足したら `tests/ui.rs` に保護・エスケープ・秘密値非出力の検査を足す。
