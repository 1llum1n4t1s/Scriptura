# 設計判断

- **同意と `propose` を廃止し、保守は commit と push だけにする**: 登録操作と二重で保守が溜まる原因だった。安全は「登録しない限り動かない」「`enable` が remote・ブランチ・upstream を必須にする」「保守後検査に違反したら commit しない」で保つ。
- **旧設定は読み込み時に schema 3 へ変換し、同意あり・実効 `push` の登録だけ動かし続ける**: 他は `paused` と `migrated_from` で止め、`enable` でだけ再開する。`policy` の `all` / `remote-owner` は、同意あり・既定 `push` でなければ `explicit` へ戻す。保存は hook が 1 回だけ行い、閲覧・`status`・`doctor` は書かない。`<state>/proposals/` は触らない。
- **hook の経路で tokio を使わない**: hook・CLI は同期の Rust だけ。tokio は `ui::run` の中だけで、feature `ui` なしでは axum・askama・tokio をリンクしない。
- **Setup 版の適用はログオン時と管理画面の「更新をインストール」だけにする**: Velopack の適用が他プロセスを強制終了するため、日中は自動適用しない。確認・取得は hook の後に同期で 1 回、適用前に署名者を検証する。ログオン時の常駐は、先に常駐すると `busy` で更新が止まるため、`update-apply` が適用を依頼しなかったときだけ後から起動する。画面のインストールは同じ検証を通し、他の Scriptura が動いていれば見送る。
- **管理画面の終了は実行中の `run-now` ジョブを待つ**: worker を途中で止めないため。
- **常駐は OS の API を直接使う**: Windows は `Shell_NotifyIconW`、macOS は `NSStatusItem`（crate を足さない）。Linux は対応しない。非常駐のセッションは 60 分で失効し、常駐は失効させない。「開く」のたびに使い捨て鍵を再発行する。ログオン時の常駐は Setup 版だけで既定 ON（`ui --autostart off` で OFF。保存済みの OFF は保つ）。
- **worker の `max_budget_usd` は持たない**: 使用量はタイムアウトとモデル・effort で調整する（既定は Sonnet の medium、1200 秒）。廃止したキーは未知キーと同じく拒否する。
- **worker のモデル名・effort は選択式にする**: 固定表から選ばせる。モデル一覧の取得は、`ANTHROPIC_API_KEY` が既にあるときだけ、明示の更新操作（POST）でだけ行い、結果はメモリだけに置く。保存済みの未知の値は残し、新しい値は固定表・取得結果・保存済みのどれにも一致しなければ拒否する。
- **上限・必須見出しの違反で保守を止めず、再実行・分割・警告つき commit で完了させる**: `ready` のまま止めると HEAD が進んで以後保守されなくなる（実際に詰まった）。(1) 最初の指示で超過文書を上限の 90% 以下へ収めることを必須にする。(2) worker 直後に `kinds::check_documents` で検査し、超過が残れば違反を数値つきで示す再実行を最大 2 回（`MAX_FIXUPS`）同じ hook 内で行う（残り 120 秒未満なら行わない）。AGENTS は階層（ルートから子の合計）も対象で、必要削減量（合計 − 29,999）を出し、最大 3 回（`MAX_AGENTS_FIXUPS`）、超過量が縮まなければ打ち切る。個人用 override は編集不可で、編集できる分で吸収できなければハードとする。(3) 残った違反は、ソフト（利用者設定の上限・必須見出し）なら警告つきで commit・push し、通知と `run-now --json` の `warnings` で知らせる。ハード（AGENTS の 30,000 バイト・階層超過、CHANGELOG のリリース済みエントリの変更、検査不能）は `discard_outputs` が出力を破棄して `complete` にし（履歴は `rejected`）、現在の内容が `after` と一致する許可パスだけを戻す。利用者が触った可能性のあるパスは戻さず知らせる。`core.autocrlf=true` で `git restore` が CRLF に変えたときは、HEAD の blob が変更前と同じ場合だけ変換なしで書き直す。(4) 旧版の `ready` / `worker_failed` は HEAD が進んだ時点で同じ破棄をして新しい保守にする。
- **分割先の新規ファイル名は worker が内容に合わせて付け、Rust が形式と件数を検査する**: 固定の候補一覧から選ばせると、日本語の見出しでは `section-NN.md` のような意味の分からない名前になるため。上限を設定した CHANGELOG 以外の種類は、既定で `docs/<id>`（`[kinds.<id>] split_dir`）へ詳細を移せる。分割先直下の追跡済み `*.md` は編集でき、新規作成は安全の条件を満たす分割先の直下だけを許す（`restricted` では `Edit(./<dir>/*.md)` を足す）。許可規則の大文字小文字の扱いに頼らず、worker の終了後の Rust の検査を最終の防御にし、違反は権限モードに関係なく commit しない。違反したファイルは自動で消さない。件数は追跡済みと新規を合わせて 1 種類 20 件まで。分割先にも同じ上限を 1 ファイルごとに掛ける。既存の `section-NN.md` は自動で改名しない。名前が内容を表すかは検査しない。既定が他の対象・分割先・機密パターンと重なれば分割しない。入れ子の AGENTS.md へは分割しない。
- **保守履歴は「worker を起動した保守」と「失敗した回」だけを、結果と範囲だけで残す**: worker を起動せず失敗もしない回は残さない（同条件の失敗は 1 行にまとめる）。本文・差分は複製せず、パス・行数・範囲・コミット・理由だけ持つ。書き込みはベストエフォートで、失敗しても保守の契約を揺るがさない。上限はリポジトリごと 200 件・全体 2,000 件。状態 DB の版は上げず表だけ足す。
- **Git の読み取りの重複は、状態を変える操作を挟まない 1 つの連鎖の中だけで省く**: Windows の git 起動は約 40ms で、1 回の保守が数十回起動するため。共有は構造体・引数で明示し、グローバル・static のキャッシュは持たない。worker・commit・push・`restore`・fetch をまたぐ値と、安全確認の取り直しは省かない。失敗した取得は保持しない。
- **管理画面の時刻は表示だけ整える**: 保存形式（RFC 3339）と CLI の JSON は変えず、表示だけローカル時刻にする。
- **プラグインのスキルは CLI を呼ぶ薄い層にする**: 判断・検証・書き込みは `scriptura <cmd> --json` に集める。
